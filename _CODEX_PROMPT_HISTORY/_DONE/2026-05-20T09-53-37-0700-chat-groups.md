# Chat groups

## Prompt

```text
Implement the first SS graph query/read layer: chat summaries.

Context:
We are on branch Ftr:ss-move.

Current SS graph is functioning and stable:

* messages
* chats
* handles
* chat_to_message
* chat_to_handle

Incremental continuation and idempotence are already proven.

Goal:
Prove that the canonical SS graph can directly answer the app’s core user-facing question:

Show me chats grouped by participants.

This slice is intentionally:

* read/query focused
* topology focused
* not schema-expansion focused

No AddressBook integration yet.
No UI polish.
No production feature architecture yet.

Implement:

1. Chat summary query layer

Create a focused read/query layer that produces chat summaries from working_ss.db topology.

Suggested location:

application/chat_summaries/

or equivalent lightweight structure.

Do NOT over-abstract.

2. Chat summary fields

Each summary should include at minimum:

chat_ss_id
participant_handles
participant_count
is_group
message_count
last_message_at_utc
last_message_text

Definitions:

participant_handles:

* derived from working_ss.chat_to_handle
* joined to working_ss.handles

participant_count:

* count of distinct handles in the chat

is_group:

participant_count > 1

message_count:

* count from working_ss.chat_to_message

last_message_at_utc:

* latest message date in chat

last_message_text:

* latest non-null message text in chat if practical
* otherwise latest message text
* NULL acceptable if no text exists

3. Query philosophy

This is a graph query proof.

Do:

* derive from canonical SS topology
* use working_ss.db only
* use ss_id endpoints only

Do NOT:

* use GUID relationships
* use source_rowid in working queries
* add legacy-style canonicalization layers
* introduce complex repository abstractions

4. Dev panel display

Add a crude readout/table/list to the SS dev panel.

Requirements:

* sortable/readable enough for inspection
* no styling work
* no production UI work

Display:

* participant handles
* participant_count
* is_group
* message_count
* latest message preview
* latest message timestamp

5. Diagnostics

Add a few useful sanity counts if helpful:

group chat count
single-participant chat count
largest participant count
largest message count

6. Tests

Add focused tests for:

* participant_count derivation
* is_group derivation
* latest message resolution
* topology joins
* chats with multiple handles
* chats with one handle
* chats with no text messages
* no duplicate participant rows
* stable ordering if implemented

7. Constraints

Do NOT:

* add AddressBook integration
* merge handles into contacts
* redesign graph architecture
* add caching systems
* add new orchestration layers
* add production UI abstractions

Do:

* prove SS graph usability
* derive semantics from topology
* keep implementation lean
* keep working queries ss_id-based

Verification:

* run against real data
* inspect real group chats
* confirm participant grouping behaves correctly
* dart analyze on changed files

Response style:
Keep response under 12 lines.

Report only:

* files changed
* query layer added
* sample observed output
* tests run
* blockers if any
```
