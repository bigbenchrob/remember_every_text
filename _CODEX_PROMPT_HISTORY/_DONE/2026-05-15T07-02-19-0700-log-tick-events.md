# Log tick events

## Prompt

```text
Task: Add per-tick causal event tracing to the shadow endurance log

Context

The current shadow endurance log records an end-of-tick status summary.

This is useful, but it can hide important transient causal events.

Observed problem:

If shadow import/migration executes quickly inside one polling tick, the final end-of-tick summary may show:

ImportDecision.doNothing
MessageSyncState.sourceAndLedgerCursorsMatch
MigrationDecision.doNothing
MessageMigrationState.projectionCaughtUp

That makes it look like no work was needed.

But inside the tick, the real sequence may have been:

source ahead detected
→ import decision became considerIncrementalImport
→ shadow import executed
→ migration decision became considerShadowMigration
→ shadow migration executed
→ final state resolved to doNothing / projectionCaughtUp

The end-state snapshot erases the causal path.

Goal

Add a per-tick “Tick Events” section to the endurance log so each polling sample records both:

1. What happened during the tick
2. What the final end-of-tick state was

Desired log shape

For each polling sample, include:

## Tick Events

- reader refresh started
- import delta observed: rowIdDelta=2, messageCountDelta=2
- import decision observed: ImportDecision.considerIncrementalImport
- shadow import executed: insertedMessageCount=2
- migration delta observed: messageIdDelta=2, messageCountDelta=2
- migration decision observed: MigrationDecision.considerShadowMigration
- shadow migration executed: insertedMessageCount=2
- comparison observed: import=..., migration=...

Then keep the existing end-of-tick summary:

### Behavioral assessment
...

### Shadow import
...

### Shadow migration
...

### Comparative validation
...

Architectural intent

The endurance log should now capture:

- transient causal path
- final settled state

This distinction matters because:

fast convergence can erase evidence from end-state snapshots.

The log should make it clear when:

“The system needed work, performed the work, and had already resolved by the summary.”

Implementation guidance

1. Add a per-tick event buffer/cache

At the start of each polling tick:

- clear tick events

During the tick:

- append notable observed facts
- append policy decisions
- append execution events
- append comparison observations

At the end of the tick:

- write the Tick Events section
- then write the existing status summary

2. Keep this diagnostic only

Do not allow tick event logging to affect:

- import decisions
- migration decisions
- polling cadence
- provider invalidation
- shadow execution
- production behavior

3. Capture the minimum useful events

At minimum, capture:

- tick started
- reader refresh / observation boundary invalidated
- import delta observed
- import decision observed
- shadow import executed or skipped, with reason
- migration delta observed
- migration decision observed
- shadow migration executed or skipped, with reason
- comparison observed

4. Prefer already-available values

Do not add broad new provider reads just for logging if the orchestrator already has the value.

Avoid reintroducing circular dependencies.

Do not read the dev-panel aggregate provider from inside polling orchestration.

5. Preserve end-of-tick summary

The current summary sections should remain:

- Behavioral assessment
- Shadow import
- Shadow migration
- Comparative validation

The new Tick Events section should supplement them, not replace them.

6. Keep architecture boundaries

Tick event logging is observability only.

Do not move semantic logic into the logger.

The logger should record already-derived facts/decisions/events.

Guardrails

Do not:
- change production behavior
- mutate production databases
- alter shadow import/migration semantics
- add UI work
- add retry/debounce behavior
- change polling interval
- read shadowIncrementalUpdateStatusProvider from the polling orchestrator
- create provider dependency cycles

Testing / verification

Run:

- dart analyze on changed files

If practical, add a focused unit test for log formatting or tick-event rendering.

Manual verification:

1. Start polling from steady state.
2. Send 2 Messages.app messages between ticks.
3. Confirm the next log sample includes Tick Events showing:
   - import delta observed
   - import decision considerIncrementalImport
   - shadow import executed
   - migration decision considerShadowMigration if applicable
   - shadow migration executed if applicable
4. Confirm end-of-tick summary may show doNothing / projectionCaughtUp.
5. Confirm the causal events explain how it got there.

Report:

- files changed
- how tick events are buffered
- which events are captured
- confirmation that end-of-tick summary remains
- confirmation no provider cycles were introduced
- example log snippet
```

Implemented per-tick causal event tracing in the endurance log.

Changed files:

sync_state_polling_orchestrator.dart

shadow_migration_refresh_orchestrator.dart

comparative_validation_orchestrator.dart

shadow_polling_endurance_log_writer.dart

How it works:

Each polling tick creates a local List<String> event buffer.

The orchestrators append events while they already observe facts, decisions, execution results, and comparisons.

The buffer is passed to the endurance log writer with the final end-of-tick snapshot.

No dev-panel aggregate provider is read, so no provider cycle is introduced.

Events captured:

tick started

reader refresh started

import observation boundary invalidated

import delta observed

import decision observed

shadow import executed or skipped

migration reader refresh started

migration delta observed

migration decision observed

shadow migration executed or skipped

comparison observed

The existing end-of-tick sections remain:

Behavioral assessment

Shadow import

Shadow migration

Comparative validation
