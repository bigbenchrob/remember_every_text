# review

## Prompt

```text
I would like an architectural planning pass only. Do not modify code.

Please review:

* 70-GRAPH-SYSTEM-COMPLETION-ROADMAP.md
* 71-LEGACY-DEPENDENCY-MATRIX.md

and produce a new planning document:

72-GRAPH-CHOKE-POINTS-AND-RETIREMENT-BLOCKERS.md

The purpose of this document is to identify the highest-leverage remaining migration work and prevent us from spending effort on low-leverage dependency removal.

The roadmap tells us where we are going.

The dependency matrix tells us what remains.

This new document should answer:

Which remaining systems unlock the largest amount of downstream simplification?

Required Sections

1. Architectural Choke Points

Define and identify architectural choke points.

Definition:

A relatively small subsystem whose migration, replacement,
or completion removes a disproportionately large number
of downstream legacy dependencies.

For each choke point provide:

* description
* current state
* dependencies blocked by it
* estimated leverage
* recommended migration order

Evaluate at minimum:

* SearchService
* Search identity model
* Display Identity Resolver
* Contact Identity Layer
* MessageEvidenceScope construction
* Graph Readiness Provider
* ChatDbChangeMonitor
* ConversationGraphBuildService
* Graph lifecycle orchestration
* Attachment archive/recovery identity mapping

Feel free to identify additional choke points.

⸻

2. Compatibility Bridges

Create an explicit inventory of compatibility bridges.

Definition:

Temporary logic whose purpose is to connect
legacy identity, lifecycle, or selection systems
to graph-native systems.

For each bridge identify:

* bridge owner
* source side
* destination side
* why it exists
* whether it is intentional
* what must happen before it can be removed

The goal is to distinguish:

temporary compatibility bridge

from

accidental architectural debt

⸻

3. Retirement Blockers

Create an explicit inventory of blockers preventing retirement of:

working.db
macos_import.db
legacy read models
legacy projection systems

For each blocker provide:

* blocker description
* affected systems
* removal criteria
* recommended sequencing

This section should make it obvious why certain legacy systems cannot yet be deleted.

⸻

4. Overlay Identity Audit

Perform a planning-level audit of overlay identity usage.

The graph migration is moving ordinary evidence selection toward:

ss_id

However overlays may still contain identity references based on:

* GUIDs
* working.db IDs
* row IDs
* legacy participant identity
* legacy chat identity

Identify:

* known overlay identity dependencies
* suspected overlay identity dependencies
* areas requiring verification

Document:

What identity forms exist?
What identity forms should exist?
What bridge strategy is required?

Do not change implementation yet.

The goal is to avoid discovering overlay identity problems after Search and Identity migration are underway.

⸻

5. Leverage-Based Migration Order

Starting from the roadmap and dependency matrix, propose a migration order based on leverage rather than category.

The document should explicitly evaluate whether:

Search
→ Contact Identity
→ Lifecycle

is preferable to:

Lifecycle
→ Search
→ Contact Identity

and explain why.

Provide a recommended ordering with rationale.

⸻

6. Closure Criteria

For each identified choke point, define:

Done means...

The goal is to create objective completion criteria rather than open-ended migration work.

⸻

Constraints

Do not modify production code.

Do not create implementation tasks.

This is an architectural analysis and planning document only.

Focus on leverage, dependency collapse, compatibility bridge removal, retirement blockers, and migration sequencing.

The goal is to identify the smallest set of changes that unlock the largest amount of future simplification.
```
