WHERE THE MISSING CALL LIKELY BELONGS

The missing step is probably not in the UI cassette and not in the timeline provider.

It should live in the archive merge application/service layer, immediately after archive rows are staged into:

historical_archive_import.db.messages

Current apparent flow:

Merge Into Timeline
→ validate archive folder
→ read archive chat.db
→ insert rows into historical_archive_import.db.messages
→ return result

Required flow:

Merge Into Timeline
→ validate archive folder
→ read archive chat.db
→ insert rows into historical_archive_import.db.messages
→ replay/project staged archive rows into working.db
→ refresh timeline/search/heatmap providers
→ return result

⸻

LIKELY FUNCTION BOUNDARY

Look for the method that currently produces the final result screen, likely something equivalent to:

mergeIntoTimeline(…)
importHistoricalArchive(…)
stageHistoricalArchive(…)
runArchiveMerge(…)
HistoricalArchiveMergeResolver.merge(…)

That method should not return immediately after staging.

It should call a second step, conceptually:

projectHistoricalArchiveIntoWorkingDb(batchId)

or:

replayHistoricalArchiveBatchToWorkingDb(batchId)

⸻

IMPORTANT: DO NOT MOVE THIS INTO UI

The cassette action should only dispatch the intent.

The resolver/service owns:

1. staging into historical_archive_import.db
2. projection into working.db
3. result accounting

The UI should receive only the final immutable result payload.

⸻

RESULT ACCOUNTING SHOULD DISTINGUISH TWO COUNTS

Current report says:

Messages added to timeline: 0

But the archive DB is receiving ~8,000 rows.

So the result model needs to distinguish:

* rows_staged_to_archive_db
* rows_projected_to_working_db
* rows_already_staged
* rows_already_projected
* rows_failed
* rows_without_guid_count

“Messages added to timeline” should mean:

rows_projected_to_working_db

not:

rows staged into historical_archive_import.db

The merge result is probably being returned after this succeeds:

archive chat.db → historical_archive_import.db

but before this ever runs:

historical_archive_import.db → working.db

So the fix is likely a missing service call, not a schema problem.
