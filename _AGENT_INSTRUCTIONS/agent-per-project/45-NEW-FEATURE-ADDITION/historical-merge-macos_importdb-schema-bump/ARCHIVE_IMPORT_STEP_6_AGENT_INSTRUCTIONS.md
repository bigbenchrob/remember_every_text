# Agent Instructions: Step 6A/6B — Enable Archive Import Into Canonical Ledger Only

## Purpose

We are ready to begin archive execution, but only in the smallest safe slice.

The goal of this step is to start replacing the cancelled preparation-batch behavior with a real archive import execution path that writes archive source records into the existing canonical import ledger (`macos_import.db`).

This slice must not recreate any of the spike architecture.

## Current Foundation Already Proven

The following are already complete and validated:

- `macos_import.db` is the single canonical import ledger.
- `working.db` is the disposable projection.
- `user_overlays.db` remains untouched.
- Surrogate canonical IDs are in use.
- Source-native ROWIDs are preserved only in `source_*_rowid` traceability columns.
- Current Mac import writes provenance fields:
  - `source_id`
  - `first_import_batch_id`
  - `last_import_batch_id`
- Canonical ledger timestamps are Unix epoch seconds stored as `INTEGER`.
- Migration converts ledger INTEGER timestamps back to the current `working.db` text representation.
- Current Mac onboarding/import/migration/search/timeline/heatmap have been manually validated after a clean DB rebuild.
- Archive execution is still disabled.

## Non-Negotiable Rules

1. Do not create or use `historical_archive_import.db`.
2. Do not create a parallel archive staging database.
3. Do not write archive rows directly into `working.db`.
4. Do not create archive-specific projection logic.
5. Do not make providers or UI read directly from an archive source database.
6. Do not let migration read from attached or external archive databases.
7. Do not report archive import success unless canonical ledger insertion, full migration, and required rebuild/refresh complete.
8. Do not change overlay behavior.
9. Do not broaden this slice into attachment recovery, archive deletion, or source filtering.
10. Keep the work incremental and testable.

## Step 6 Scope

This step should begin the real archive execution path, but it should remain narrowly focused.

The intended path is:

Historical archive `chat.db`
→ read source rows
→ normalize into canonical ledger inputs
→ insert/upsert into `macos_import.db`
→ later trigger full canonical migration
→ later become visible through normal `working.db` projections

For this immediate slice, focus on archive-to-ledger execution first. Do not overbuild UI polish.

## Required Behavior

### 1. Replace cancelled preparation batch with a real archive import batch

Current behavior records a cancelled preparation batch when the user clicks Begin Import.

New behavior should begin a real archive import batch for the selected historical archive source.

Batch lifecycle should be explicit:

- create batch with `chat_source_kind = historical_archive`
- create batch with the selected archive `source_id`
- set status to `running`
- set status to `succeeded` only after the intended work for this slice completes
- set status to `failed` if the slice fails
- preserve error summary if failed

Do not use cancelled preparation batches for real import execution.

### 2. Read archive source rows using an isolated source read path

Open the selected archive `chat.db` as a source database.

This source read belongs to import execution only.

Archive source data must be fully materialized into the canonical ledger before migration begins.

Migration must never depend on the archive source database being attached or open.

### 3. Write archive rows into canonical ledger tables

Archive rows must use the same canonical ledger tables as current Mac import wherever possible:

- `handles`
- `chats`
- `messages`
- `chat_to_handle`
- `chat_to_message`
- `attachments`, if already safely supported by existing canonical importer logic
- recovered/unlinked tables only when source joins are genuinely missing

Every major archive row must carry:

- archive `source_id`
- `first_import_batch_id`
- `last_import_batch_id`
- source-native rowid in the appropriate `source_*_rowid` column

Canonical `id` values must remain ledger-local surrogate IDs generated by SQLite.

Do not write source-native ROWIDs into canonical `id` columns.

### 4. Use GUID-based dedupe at ledger insertion

Message and chat dedupe must use canonical GUID rules at ledger insertion.

If a message GUID already exists:

- do not insert a duplicate canonical message row
- update `last_import_batch_id` only where the provenance contract says that is correct
- record the row as deduplicated/skipped in batch accounting

If a GUID is missing or unusable:

- do not invent fuzzy identity
- count it explicitly as failed or missing-GUID according to the existing result/accounting contract

### 5. Preserve canonical timestamp rules

Archive timestamps must be normalized through the shared date conversion utilities.

Ledger timestamp columns must store Unix epoch seconds as `INTEGER`.

Do not store ISO strings in `macos_import.db` canonical timestamp columns.

### 6. Migration trigger must remain canonical

After successful archive ledger ingestion, archive visibility must come from a full canonical migration cycle.

Do not write a custom archive projector.

Do not manually insert archive rows into `working.db`.

If this slice does not yet trigger migration, the UI/result text must say so clearly and must not claim messages are visible.

## Recommended Micro-Slice Boundaries

Prefer these small steps rather than one large edit.

### 6A: Real batch lifecycle only

- Replace cancelled preparation batch with a real historical archive batch lifecycle.
- Do not insert archive rows yet if that keeps the slice safer.
- Add tests proving batch status transitions and source linkage.

### 6B: Ledger insertion for one canonical family

- Start with handles/chats/messages only.
- Prove surrogate IDs, source rowids, source_id, and batch IDs are correct.
- Add tests before adding more table families.

### 6C: Join reconstruction

- Add `chat_to_message` and `chat_to_handle` using canonical IDs, not source ROWIDs.
- Add tests proving no orphan joins.

### 6D: Full archive ledger import

- Add remaining safe table families.
- Add dedupe/idempotency tests.

### 6E: Trigger canonical migration

- Only after ledger insertion is proven.
- Use normal migration orchestrator.
- Add tests proving archive rows become visible through `working.db` only after migration.

## Required Tests For This Step

Add focused tests before broad validation.

At minimum, cover:

1. Begin Import creates a real historical archive batch, not a cancelled preparation batch.
2. Archive batch references the correct historical archive `ledger_sources.id`.
3. Archive rows inserted into canonical tables get archive `source_id`.
4. Archive rows get `first_import_batch_id` and `last_import_batch_id`.
5. Source-native ROWIDs are preserved only in `source_*_rowid` columns.
6. Canonical IDs remain surrogate IDs.
7. Message GUID dedupe prevents duplicate canonical message rows.
8. Re-importing the same archive is idempotent.
9. Missing or unusable message GUIDs are counted explicitly and not heuristically merged.
10. Migration is not reading from the archive source database.
11. No archive rows are written directly into `working.db`.
12. Archive execution does not touch `user_overlays.db`.

## Required Validation Before Reporting Done

Run focused tests for the touched archive workflow/import files.

Also run the current live-path regression suite to prove current Mac import still works.

Do not report success without stating:

- whether archive rows are now written to `macos_import.db`
- whether full migration is triggered in this slice or intentionally deferred
- whether archive rows are expected to be visible in the UI after this slice
- which tests prove idempotency/dedupe/source provenance

## Explicit Non-Goals For This Slice

Do not implement:

- archive deletion UI
- source filtering
- attachment recovery from old snapshots
- heatmap UI changes
- a new archive import DB
- direct working DB writes
- direct archive DB provider reads
- working DB timestamp schema changes
- overlay changes

## Success Definition

This slice succeeds only if archive import begins entering the canonical system safely.

A successful result means:

- historical archive source identity is used
- real archive batch identity is used
- archive rows are written to `macos_import.db` canonical tables with source provenance
- GUID dedupe and idempotency are tested
- current Mac import still works
- archive execution remains on the canonical path, not a side path

The goal is not to make the UI look finished.

The goal is to make the first real archive execution path impossible to confuse with the old spike architecture.
